# 02 · 技术栈详解

本项目技术栈分为四大层：**LLM 编排层**、**科学计算层**、**蛋白语言模型层**、**前端与基础设施层**。

```
┌─────────────────────────────────────────┐
│  前端与基础设施层                         │
│  Gradio · MCP · LangChain · Python      │
├─────────────────────────────────────────┤
│  LLM 编排层                               │
│  LangGraph · StateGraph · ToolNode      │
├─────────────────────────────────────────┤
│  蛋白语言模型层                            │
│  ESM-2 (Meta FAIR) · fair-esm · PyTorch  │
├─────────────────────────────────────────┤
│  科学计算层                                │
│  Rosetta · PyMOL · ThreadPoolExecutor   │
└─────────────────────────────────────────┘
```

## 1. LangGraph（核心框架）

### 1.1 是什么

LangGraph 是 LangChain 团队推出的**有状态多智能体编排框架**，核心抽象是 `StateGraph`（状态图）。

- 一个 Graph = 一组 Node + 一组 Edge
- Node = 处理函数（接 State，返回 State 的更新）
- Edge = 控制流（普通边、入口 `START`、出口 `END`、条件边 `add_conditional_edges`）
- State = TypedDict，自动用 reducer 合并

### 1.2 为什么不用裸 LangChain

裸 LangChain 的 AgentExecutor 是黑盒循环：调 LLM → 解析 tool_call → 调工具 → 把结果塞回 messages → 再调 LLM，**你控制不了执行顺序**。

LangGraph 让你**显式画出每一步**：

```python
sg.add_edge(START, "step1_llm")
sg.add_conditional_edges("step1_llm", route, {"tool": "step1_tool", "__next__": END})
sg.add_conditional_edges("step1_tool", route2, {"next": "step2_llm", "repair": "repair"})
```

这种**图结构**的好处：
- 执行顺序**写在图里**，不靠 prompt 约束
- 错误恢复走专门分支，不靠 prompt 注入
- 每一步的输入输出**可观测、可回放**

### 1.3 本项目的关键使用

```python
# 主图 6 节点
workflow.add_node("router", router_node)
workflow.add_node("pipeline", build_pipeline_subgraph())
workflow.add_node("reply", reply_node)
workflow.add_node("reply_tools", reply_tools_node)
workflow.add_node("skempi_eval", skempi_eval_node)
workflow.add_node("summarize", summarize_node)

# 流水子图 10 节点
# step1_llm / step1_tool / step2_llm / step2_tool / disorder_check /
# step3_llm / step3_tool / repair / repair_tools / progress_poll
```

`build_pipeline_subgraph()` 是核心工厂函数，把三段式流水线封装成可复用子图。

### 1.4 ToolNode 与 bind_tools

每个 LLM 节点都做：

```python
step_llm = llm.bind_tools([step1_only_tool])  # schema 物理限制
```

LLM 调工具时只能看到这一个工具，想调别的工具也调不出来——**这是 schema 层的硬约束**，比 prompt 里写"绝对禁止调用 X"靠谱得多。

`ToolNode` 是 LangGraph 预置的节点，自动遍历 AIMessage.tool_calls 并执行对应工具。本项目继承它做 `TaskAwareToolNode`，注入 thread_id 作为工作区。

## 2. LangChain（基础库）

### 2.1 是什么

LangChain 是 LLM 应用开发的事实标准库。本项目用它做：

- `@tool` 装饰器：把 Python 函数注册为 LLM 可调用的工具
- `ChatOpenAI`：兼容 OpenAI 协议的 LLM 客户端
- `ChatPromptTemplate` / `SystemMessage` / `HumanMessage` / `AIMessage` / `ToolMessage`：消息类型
- `Chroma` + `OpenAIEmbeddings` + `TextLoader` + `RecursiveCharacterTextSplitter`：RAG 检索增强生成（用于搜索 Rosetta 文档）

### 2.2 消息类型速查

| 类型 | 谁产生 | 内容 |
|---|---|---|
| `SystemMessage` | 系统 | 角色设定 / 工具权限说明 |
| `HumanMessage` | 用户或代理节点 | 用户输入 / 进度播报 |
| `AIMessage` | LLM | 回复文本 + `tool_calls` 字段 |
| `ToolMessage` | 工具执行 | 工具结果字符串 |

## 3. Rosetta（科学计算核心）

### 3.1 是什么

[Rosetta](https://www.rosettacommons.org/) 是华盛顿大学 Baker 实验室维护的开源分子建模软件包，用 C++ 编写，提供：

- 蛋白结构预测与设计
- 能量函数（force field）评估
- 蒙特卡洛 / 模拟退火优化
- 蛋白-蛋白对接
- 配体参数化

### 3.2 本项目用到的三个工具

| 工具 | 作用 |
|---|---|
| `molfile_to_params.py` | 把 `ligand.pdb/mol2` 转为 Rosetta 可识别的 `.params` 拓扑文件 |
| `relax.linuxgccrelease -relax:cartesian` | Cartesian 空间弛豫（带配体清洗 PDB） |
| `cartesian_ddg` | 饱和突变 ΔΔG 扫描 |

### 3.3 为什么用 Rosetta ΔΔG 预测

ΔΔG = ΔG(mutant) - ΔG(wildtype)，单位 REU（Rosetta Energy Unit）。

- ΔΔG < 0：突变后蛋白更稳定
- ΔΔG > 0：突变后蛋白不稳定
- 与实验亲和力变化 ΔΔG_bind 高度相关（但不完全等价）

Rosetta 的 `ref2015_cart` 能量函数在饱和突变扫描任务上是目前最成熟的开源方案之一。

## 4. ESM-2（蛋白质语言模型）

### 4.1 是什么

[ESM-2](https://github.com/facebookresearch/esm) 是 Meta FAIR 团队用Transformer 训练的大规模蛋白语言模型，输入氨基酸序列，输出每个残基的上下文嵌入。

### 4.2 本项目的用法

不是用 ESM-2 做突变预测，而是用它的 **disorder 预测**：

```python
from esm import pretrained
model, alphabet = pretrained.esm2_t12_35M_UR50D()
batch_converter = alphabet.get_batch_converter()
```

输入 PDB 的氨基酸序列 → 输出每个残基的 disorder 概率（0-1）。阈值 0.5 视为无序区域。

### 4.3 为什么需要 disorder 过滤

MD 模拟的结构（如 `best_relaxed_98840.pdb` 来自 1MC9 经 MD）会把无序区域"强行稳定"成有构象——**这是 MD 模拟的人为结果**，不是真实结构。在这些区域跑 Rosetta ΔΔG 预测无意义（甚至误导）。

ESM-2 disorder 检测可以提前预警：在 step2 弛豫完成后、step3 突变前，自动跳过 disorder 概率高的位点。

### 4.4 模型选择

本项目用 `esm2_t12_35M_UR50D`（35M 参数的小模型）：
- 体积小（~60MB），下载快
- 在 disorder 预测任务上准确度够用
- 可以跑在 CPU 上（用 `setup_blackwell.sh` 切换到 GPU）

### 4.5 双策略自动回退

- **优先 ESM-2**：本地推理，需要 `fair-esm + torch`
- **失败回退**：B-factor 归一化 + 残基序号 gap 启发式（无外部依赖）

不装 fair-esm 也能跑，精度低一些。

## 5. PyMOL（结构可视化与配体提取）

### 5.1 是什么

[PyMOL](https://pymol.org/) 是最常用的分子可视化开源软件。本项目不调用它的 GUI，而是用它的 Python API / 命令行模式。

### 5.2 用法

```bash
pymol -c -d "load protein.pdb, complex; save ligand.pdb, complex and organic"
```

这条命令：
1. 加载蛋白-配体复合物
2. 选择 "organic" 选择子集（即非蛋白非水分子 = 配体）
3. 单独保存为 `ligand.pdb`

### 5.3 在项目中的位置

仅在用户上传**复合物 PDB** 时触发；如果用户单独上传了配体文件，就跳过这步。

## 7. Chroma + RAG（检索增强生成）

### 7.1 是什么

[Chroma](https://www.trychroma.com/) 是轻量级向量数据库，本项目用它做：

- 文档嵌入：`OpenAIEmbeddings`
- 文档加载：`TextLoader`
- 文档切分：`RecursiveCharacterTextSplitter`

### 7.2 在项目中的角色

`search_rosetta_docs` 工具让 LLM 能检索 `rosetta_manuals/报错解决笔记.txt`，遇到陌生报错时调 RAG 找到解决方案。这是 `repair` 分支的核心能力之一。

## 8. ThreadPoolExecutor（并发执行）

### 8.1 是什么

Python 标准库 `concurrent.futures.ThreadPoolExecutor`，**线程池**用于 IO 密集型并发（本项目里全是 subprocess 启动 Rosetta，所以线程池比进程池合适）。

### 8.2 在项目中的用法

不是直接在主 Python 进程里用，而是把 ThreadPoolExecutor 写进**生成的 shell 脚本里**：

```python
# 在 rosetta_tools.py 里动态生成弛豫脚本
script = f"""
from concurrent.futures import ThreadPoolExecutor
def execute(i):
    subprocess.run(f"relax.linuxgccrelease ... -out:prefix S{i}_")

with ThreadPoolExecutor(max_workers={nstruct}) as pool:
    for i in range(1, {nstruct} + 1):
        pool.submit(execute, i)
"""
```

### 8.3 为什么是 ThreadPoolExecutor 而不是 multiprocessing

Rosetta 的 `relax` / `cartesian_ddg` 是**外部进程**，每个任务自带并行（Rosetta 内部用 MPI/OpenMP）。Python 主线程只需要 `subprocess.Popen` + 等待，IO 等待时让其他线程跑——线程池完美匹配这个模型。

## 9. Pydantic / TypedDict（状态建模）

### 9.1 在项目中的角色

```python
class AgentState(TypedDict):
    messages: Annotated[list, add_messages]
    intent: str
    pipeline_step: int
    failed_step: int
    retry_count: int
    progress_polls: int
    progress_done: bool
    disordered_sites: list
    disorder_scores: dict
```

TypedDict 让 LangGraph 知道每个字段的 reducer（如 `add_messages` 自动合并消息列表，其他字段默认覆盖）。这种**结构化状态**是 LangGraph 比 LangChain 黑盒循环好的关键。

## 13. 技术选型的替代方案对比

| 当前选型 | 替代方案 | 为什么没选 |
|---|---|---|
| LangGraph | LangChain AgentExecutor | 黑盒循环，控制不了顺序 |
| LangGraph | CrewAI / AutoGen | LangGraph 更底层，状态可控 |
| ESM-2 t12 35M | ESM-2 t30 / t33 | 体积太大（>3GB），35M 够用 |
| Chroma | FAISS / Milvus | Chroma 集成最简单 |
| Gradio | Streamlit | Gradio 的 Chatbot 更适合 Agent |
| ThreadPoolExecutor | multiprocessing.Pool | 任务是 subprocess，线程池更合适 |
| OpenAI 兼容 API | 直接调 GPT-4 | 用国产/开源 LLM 更灵活 |
