# 07 · 错误恢复与性能优化

## 1. 错误恢复机制（repair 分支）

### 1.1 整体设计

Rosetta 在科学计算里**极其容易出错**：
- 配体参数化失败（CONECT 记录不全）
- 弛豫中途 `score.sc` 写不出来（IO 阻塞）
- 突变扫描报 "Unable to find residue"（编号映射错）

传统方式是把错误处理逻辑写进 prompt，让 LLM "智能"重试——但 LLM 容易死循环重复同一个错误。

本项目用**专用 repair 分支**接管错误恢复，**完全脱离主 prompt**：

```python
REPAIR_TOOLS = [check_logs, diagnose_and_fix, auto_repair]
repair_llm = llm.bind_tools(REPAIR_TOOLS)
```

### 1.2 错误检测机制

```python
def _is_tool_error(msg) -> bool:
    if not isinstance(msg, ToolMessage):
        return False
    content = str(msg.content)
    return ("【执行报错】" in content) or ("【系统异常】" in content) or ("【执行失败】" in content)
```

**约定**：所有工具的报错必须以 `【执行报错】` / `【系统异常】` / `【执行失败】` 开头，路由层才能识别。

工具内部示例：

```python
@tool
def parameterize_ligand(ligand_path: str = "ligand.pdb") -> str:
    try:
        # ... 实际逻辑
        return f"✅ 参数化成功：{params_file}"
    except FileNotFoundError as e:
        return f"【执行报错】配体文件不存在：{ligand_path}"
    except subprocess.CalledProcessError as e:
        return f"【系统异常】molfile_to_params.py 退出码 {e.returncode}：{e.stderr[:500]}"
```

### 1.3 失败状态写入

```python
def _make_step_tool_node(step_num: int, bound_tools):
    inner = TaskAwareToolNode(bound_tools)

    def _node(state, config=None, **kwargs):
        result = inner.invoke(state, config=config, **kwargs)
        new_msgs = result.get("messages", [])
        update = {"messages": new_msgs}
        last = new_msgs[-1] if new_msgs else None
        if last and _is_tool_error(last):
            update["failed_step"] = step_num
            update["retry_count"] = state.get("retry_count", 0) + 1
        return update

    return _node
```

**关键状态字段**：
- `failed_step`：最近失败步骤（1/2/3）
- `retry_count`：累计重试次数

### 1.4 repair 节点路由

```python
def _post_tool_route(next_node: str):
    def _route(state):
        last = state["messages"][-1]
        if _is_tool_error(last):
            return "repair"
        return next_node
    return _route
```

每个 `stepX_tool` 节点出口都用这个路由函数，**成功→下一个节点，失败→repair**。

### 1.5 repair 节点本身

```python
def repair_node(state):
    sys_prompt = (
        "你是【自动修复 Agent】。当前流水线某一步刚报错，你的任务是："
        "调用合适的诊断/修复工具（check_logs / diagnose_and_fix / auto_repair）定位问题，然后直接给出修复建议。"
        "严禁重复触发同一报错工具；如确实无法自动恢复，请明确告知放弃。"
    )
    response = repair_llm.invoke([SystemMessage(content=sys_prompt)] + list(state["messages"]))
    return {"messages": [response]}
```

### 1.6 repair_tools 节点（执行修复工具）

```python
sg.add_node("repair_tools", TaskAwareToolNode(REPAIR_TOOLS))

sg.add_conditional_edges("repair", repair_route,
    {"repair_tools": "repair_tools", "__end__": "__end__"})
```

`repair_route` 检查 LLM 是否产生 tool_call，有则调 `repair_tools`，否则放弃。

### 1.7 回退路由（最关键）

```python
def repair_back_route(state):
    """repair_tools 出口：retry_count 超限 → 放弃；否则回到失败的那一步"""
    if state.get("retry_count", 0) > MAX_RETRIES:
        return "__end__"
    return {
        1: "step1_llm",
        2: "step2_llm",
        3: "step3_llm",
    }.get(state.get("failed_step", 1), "__end__")

sg.add_conditional_edges("repair_tools", repair_back_route,
    {"step1_llm": "step1_llm", "step2_llm": "step2_llm", "step3_llm": "step3_llm", "__end__": "__end__"})
```

**三道防线**：

| 防线 | 机制 | 作用 |
|---|---|---|
| 1 | retry_count 上限 | 防止死循环（MAX_RETRIES=2，最多 2 次重试） |
| 2 | 按 failed_step 路由 | 精确回到失败步骤，不重跑成功的 |
| 3 | 专用 REPAIR_TOOLS | 不让主流程的 LLM 误调修复工具 |

### 1.8 修复工具的实现

#### check_logs

```python
@tool
def check_logs(log_path: str, lines: int = 20) -> str:
    """仅读日志最后 N 行（节省 token）"""
    if not os.path.isabs(log_path):
        log_path = os.path.join(current_workspace.get(), log_path)

    if not os.path.exists(log_path):
        return f"【日志排查失败】未找到文件 {log_path}。"

    result = subprocess.run(f"tail -n {lines} {log_path}", shell=True, capture_output=True, text=True)
    if result.returncode == 0:
        return f"【日志截取成功】{log_path} 最后 {lines} 行：\n{result.stdout}"
    return f"【日志截取报错】{result.stderr}"
```

**关键设计**：默认 20 行，避免日志太大爆 context window。

### 1.9 完整错误恢复流程示例

假设 `run_cartesian_relax` 报"配体未找到 .params"：

```
step2_tool
  │ 报【执行报错】配体未找到 .params
  ▼
repair
  │ 调 diagnose_and_fix("run_cartesian_relax")
  ▼
repair_tools
  │ 诊断报告："step2 失败因 step1 输出的 .params 未生成"
  ▼
repair_back_route
  │ retry_count=1 ≤ MAX_RETRIES=2, failed_step=2
  ▼
step2_llm（重试）
  │ （如果 LLM 自己判断需要先调 step1）
  ▼
```

注意：**repair 不直接重试 step2，而是回到 step2_llm 让 LLM 重新决定**——这给 LLM 一个基于诊断报告重新规划的机会。

## 2. 性能优化

### 2.1 整体优化目标

把单蛋白饱和突变从"天级"压缩到"小时级"。

### 2.2 三层并发架构

```
┌─────────────────────────────────────────────┐
│  Level 1：用户并发                            │
│  Gradio 支持多用户同时提交任务                  │
│  contextvars 隔离工作区                        │
└─────────────────────────────────────────────┘
                     │
┌─────────────────────────────────────────────┐
│  Level 2：步骤内并发                           │
│  step2 弛豫：3 路 nstruct 并发                │
│  step3 突变扫描：jobs 路并发                   │
└─────────────────────────────────────────────┘
                     │
┌─────────────────────────────────────────────┐
│  Level 3：Rosetta 内部并行                     │
│  Rosetta 自己用 MPI/OpenMP                    │
│  进程级并行（外部进程池）                       │
└─────────────────────────────────────────────┘
```

### 2.3 step2 弛豫的并发实现

在 `run_cartesian_relax` 里**动态生成 Python 脚本**：

```python
script_template = """
import subprocess, time
from concurrent.futures import ThreadPoolExecutor

def execute(i):
    cmd = f"""
{rosetta_bin}/relax.linuxgccrelease \\
    -s complex.pdb \\
    -relax:cartesian \\
    -score:weights ref2015_cart \\
    -nstruct {nstruct} \\
    -out:prefix S{i}_
    """
    return subprocess.run(cmd, shell=True, capture_output=True)

print(f"开始多核并发弛豫 (共 {nstruct} 个构象)...")
with ThreadPoolExecutor(max_workers={nstruct}) as pool:
    futures = [pool.submit(execute, i) for i in range(1, {nstruct} + 1)]
    for f in futures:
        f.result()
"""
```

**关键设计**：
- `ThreadPoolExecutor` 而不是 `multiprocessing.Pool`，因为任务是 subprocess，IO 等待多
- `max_workers = nstruct = 3`：3 个弛豫任务并发
- 主 Python 进程只负责调度，不参与计算

### 2.4 step3 突变扫描的并发实现

在 `run_saturation_mutagenesis` 里**动态生成执行脚本**：

```python
# 1. 解析 target_resnum
# 例："76,73" → ["76", "73"]

# 2. 对每个位点 × 19 氨基酸 生成 (n × 19) 个任务
tasks = []
for site in sites:
    for aa in amino_acids:
        tasks.append({
            "pdb": wt_relaxed_pdb,
            "resnum": site,
            "mut_to": aa,
            "params_file": params_file,
        })

# 3. 生成执行脚本（含 ThreadPoolExecutor + 错峰延迟）
script = f"""
import subprocess, time
from concurrent.futures import ThreadPoolExecutor

def execute(task):
    cmd = f'''
{rosetta_bin}/cartesian_ddg.linuxgccrelease \\
    -s ${{task["pdb"]}} \\
    -ddg:mut_file mutations_${{task["resnum"]}}_${{task["mut_to"]}}.txt \\
    -ddg:iterations 3
    '''
    subprocess.run(cmd, shell=True, capture_output=True)

with ThreadPoolExecutor(max_workers={jobs}) as pool:
    for task in tasks:
        pool.submit(execute, task)
        time.sleep({delay})  # 错峰延迟，避免瞬时打挂服务器
"""
```

**关键设计**：
- `jobs` 参数：用户控制并发数（默认 10，CLI 可调到 48）
- `delay` 参数：错峰延迟（默认 1.5 秒），避免瞬时 100 个任务打挂服务器
- 768 核 HPC 上 `jobs=48, delay=1.5` 是经过调优的配置

### 2.5 并发数与延迟的调优经验

| HPC 规模 | 推荐 jobs | 推荐 delay |
|---|---|---|
| 桌面 8 核 | 4 | 1.0 |
| 服务器 64 核 | 16 | 1.5 |
| HPC 256 核 | 32 | 2.0 |
| HPC 768 核 | 48 | 1.5 |

**经验**：
- jobs 太高 → IO 排队 + Rosetta 启动开销大
- jobs 太低 → CPU 利用率不足
- delay 太小 → 瞬时资源竞争
- delay 太大 → 总时间被拉长

**调优原则**：先测 Rosetta 单任务 IO 时间 → jobs × 单任务 IO < 总内存带宽 / 8

### 2.6 contextvars 线程隔离

```python
import contextvars
current_workspace = contextvars.ContextVar('current_workspace', default='.')
```

**为什么需要**：Gradio 是多用户 Web 服务，多个用户可能同时提交任务。如果用全局变量，多任务并发会**互相覆盖工作区**。

`contextvars` 是 Python 3.7+ 引入的**协程/线程安全**上下文变量。每个 LangGraph thread（任务）独立，互不干扰。

### 2.7 后台异步轮询（progress_poll）

step3 提交后**不是阻塞等待**，而是后台跑：

**好处**：用户提交后立即拿到"已开始跑"的反馈，后台计算进度可见。

### 2.8 上下文窗口保护

LLM context window 是稀缺资源。本项目多处保护：

#### 2.8.1 工具结果截断

```python
MAX_TOOL_RESULT_CHARS = 16000

def _truncate_tool_result(content: str, max_chars: int) -> str:
    if len(content) <= max_chars:
        return content
    half = max_chars // 2
    return f"{content[:half]}\n\n... [已截断 {len(content) - max_chars} 字符] ...\n\n{content[-half:]}"
```

超 16000 字符的 ToolMessage **首尾各保留一半**，中间省略。

msg = HumanMessage(

## 3. 性能数据（实测）

在 768 核 HPC 服务器上（`amax` 集群）的实测数据：

| 任务规模 | 顺序执行 | 并发 jobs=48 | 加速比 |
|---|---|---|---|
| 1 个位点饱和突变（19 个突变体） | ~6 小时 | ~10 分钟 | 36x |
| 5 个位点（95 个突变体） | ~30 小时 | ~45 分钟 | 40x |
| 10 个位点（190 个突变体） | ~60 小时 | ~1.5 小时 | 40x |

（具体数值因 Rosetta 版本和蛋白大小而异）

## 4. 性能调优 Checklist

如果你想进一步优化：

- [ ] 调整 `nstruct=3` → 5 或 10（更多构象取平均，精度↑但时间↑）
- [ ] 调整 `jobs` 到 `0.5 × CPU核数`（平衡并发与 IO）
- [ ] 调整 `delay` 到 `单任务 IO 时间 / jobs`
- [ ] 把 ESM-2 推理切到 GPU（用 `setup_blackwell.sh`）
- [ ] 把工具结果截断阈值从 16000 调到 8000（如模型 context 小）
- [ ] 把 ThreadPoolExecutor 换成 ProcessPoolExecutor（如 Rosetta 内部有 GIL 争用）

## 5. 未来优化方向

1. **任务队列系统**：用 Celery / Redis 替代直接的 ThreadPoolExecutor
2. **断点续传**：后台任务中断后能从断点继续（目前需从头跑）
3. **预测性预取**：根据 disorder 分数，提前跳过无意义位点
4. **分布式执行**：跨多台 HPC 节点调度（用 SLURM/PBS）
5. **GPU 加速弛豫**：部分 Rosetta 模块支持 GPU（如 relax 的某些模式）
6. **结果缓存**：相同 (PDB, 位点) 的重复查询直接读缓存
